00Core principles, goals & invariants

Read this first. It is the contract the rest of the document implements — the why behind every seam. When you extend or change the framework, come back here: a change that violates an invariant below is almost always reintroducing the complecting that made the previous version unreliable.

Goals — what we optimise for

Stated as outcomes, not features. Every design decision should be traceable to one of these.

Compose, don't build

A new robot is assembled from existing cogs via a manifest. You write core logic; the framework owns the plumbing.

Fail into legibility

A fault names itself — what broke, and where — and never collapses into ambiguous silence.

Safe in the gap

The robot reaches a safe state on any fault, independently of the part that failed — never depending on recovery succeeding.

Reason locally

You can understand and change one cog without holding the whole system in your head.

Test without hardware

Core logic is pure and replayable: develop on a laptop, replay a run from a log of values.

Right-rate, not max-rate

Move only the information that's needed, when it's needed. Never flood a wire or a CPU.

Evolve without rewrites

Add a cog, re-home it to another board, or swap a control law by editing data — not by rippling code.

Principles — how we think

The tenets that produce those goals. Mostly one idea: keep concerns that can vary independently in separate homes.

  • 01 · Decomplect relentlessly. What a cog computes, when it runs, how it crosses the wire, what happens when it breaks, and where it physically lives are five separate things — never one object.
  • 02 · Prefer values and pure functions. Push as much of the system as possible into immutable data and input→output functions; reserve processes for what genuinely owns time or a socket.
  • 03 · Values carry a generation, not a clock. Every slot value carries a counter that bumps once per write. Freshness is change-detection — did the generation move within a window of the consumer's own local beat — so it needs no timestamp and no clock anywhere. Time is bought back only in the payload of the few slots that fuse, never in the core.
  • 04 · One space of named slots; name slots, not peers. Producers and consumers name slots, never each other; a value flows through a named place that holds the latest write. Whether a slot is backed by local memory, an in-process bus, or a wire is hidden from both sides.
  • 05 · Transport is meaning-blind. A link moves bytes and counts failures; it never knows what a value means. Consumers see a value, never a frame.
  • 06 · Fail-safe ≠ self-heal ≠ observability. Three separate mechanisms with three separate homes. Seeing a fault, being safe in it, and recovering from it are different jobs.
  • 07 · Supervision recovers code; an independent floor keeps the actuator fail-passive. A restart is never the safe-state mechanism. The floor guarantees bounded, non-runaway output — not task-safety, which is plant-specific (de-energising is safe for a coasting plant, a controlled fall for a balancer).
  • 08 · Configuration is data; mechanism and safety are code. Parameters live in the manifest; the safety transition graph is tested code, never bot-editable.
  • 09 · Build in dependency order. Nothing is sound until the layer beneath it is true: bounded I/O before watchdogs before health rows.

Invariants — what must stay true when you change things

The guardrails. Before merging a change, check it against every line. The italic clause is the tell — the symptom that you're about to break the invariant.

  • never  A cog owns transport, scheduling, supervision, or wire-identity. If a change has a cog reaching for a socket or a timer, a seam is missing — add the seam, don't thicken the cog.
  • never  A value crosses a slot without a generation. A frozen-but-trusted field — a value re-presented as fresh though its generation never moved — is the exact bug that made v1 unreliable.
  • never  The manifest decides whether to enter the safe state. It may set thresholds; the transition graph stays in tested code.
  • never  A second bus, a fault bus, or an optional "health cog." Faults are domain events on the one bus (L3); liveness is a priority lane in the transport (L2). Health may be scoped into per-subsystem topics (:health/limb_a…) folded to a global truth — that is many topics on the one bus, not a second bus.
  • never  More than one producer per actuator/command topic. One writer per command topic. When several sources must command one actuator, an optional arbiter cog becomes that single writer and merges their intents.
  • never  Freshness measured by a clock, or a raw time gate in a manifest. A slot is fresh when its generation moved within a fresh_for window of the monitor's local ticks — never a wall-clock age. The communication core that makes this true is §09.
  • always  Every device read is bounded; every link send is bounded by construction. L0 is a precondition — establish it before anything above assumes "non-blocking."
  • always  A new stateful component declares its restart posture and engages the floor while recovering. A restart is not a safe state; safe-then-resume or restart-clean, stated explicitly.
  • always  The pure core stays pure. Tempted to put I/O or a clock inside a step or a cook? Thread state as a value and lift the effect into the shell.
  • always  The actuator floor survives total master loss — and it is tested. The dead-man lives on a different chip; if the master supervisor dies entirely, torque still zeros on silence.
  • always  The master is sized to meet its tightest control loop, and that margin is monitored. Soft real-time is fine with headroom plus a fail-passive floor; surface worst-case loop latency before it bites — don't discover it in a fall.
  • check  Adding a bot or a cog must not require editing platform/. If it does, that's the signal to add a seam, not a feature.
  • check  A new wire field earns its place. Every frame change is a codec bump plus a parity vector — not free bytes.
  • check  Never display confidence you can't observe — and no counter without an incrementer. A green chip, or a counter hardcoded to 0, with no real signal behind it is worse than none; each counter needs a test proving it actually moves.

Capabilities — what the design delivers

The features that fall out of the principles above. Each is a property of the framework, free to every bot.

compose

Cogs composed into bots from a single manifest — composition-as-data, read once at boot.

pure

Replayable core logic: develop and unit-test on a laptop; reproduce any run from a value log.

edge

Push-down processing with backpressure by conflation — cook fast at the edge, report at the master's declared rate.

wire

Transport-transparent comms over UART / CAN / serial — the same code whether a value is local or three boards away.

health

Health truth per subsystem (scoped topics) folded to a global nominal/degraded/safe — all on the one bus — driving dashboard, log, the safe-state floor, and firmware validation.

fail-passive

Independent floors — a comms-independent dead-man at every actuator plus a master-side staleness floor — guaranteeing bounded, non-runaway output (task-safety is plant-specific).

heal

Per-device self-heal: bounded re-probe behind the device seam — online for soft sensors, at-rest only for load-bearing actuators, never live-energising one mid-task.

recover

OTP supervision on the master; task watchdog plus A/B firmware revert on the microcontrollers.

observe

Honest link counters (CRC-fail / resync / last-rx-age) that separate garbage from silence from idle-but-alive.

deadline

Control-loop deadline monitoring — per-tick latency and worst-case jitter are tracked and surfaced, so timing pressure appears on the dashboard before it appears as a fall.

re-home

Location independence — move a cog to a different board by editing data, not rewriting code.

arbitrate

Single-writer command topics. When several sources must command one actuator, an optional arbiter cog is the sole producer, merging intents by a tested priority — otherwise it isn't there.

freshness

Clock-free freshness — a generation counter plus a local beat answer "is this still good?" as binary fresh-or-stale, with no timestamp and no clock sync. The whole communication core is three primitives (§09).

mixed

Mixed runtime — a BEAM/Elixir master with C/Arduino cogs (or Elixir on the ESP32 via AtomVM).

One sentence to hold all of it: keep the cog thin, make every value carry a generation so freshness needs no clock, and keep fail-safe, self-heal and observability as three separate things — and never let a restart pretend to be a safe state.

01The system at a glance

Three independent compute units, two wire protocols, one space of named slots on the master. Signal is cooked at the edge and reported upward as low-rate values; intent flows downward and is gated by a local fail-safe floor at the actuator. Colour tells you which stratum each box belongs to. Underneath all of it sit just three ideas — slot · manifest · monitor — detailed in §09; the rest of this document is what you build out of them.

Master / platform (Elixir) Blaster (Arduino-C) Smart cog (Arduino-C) values in slots
Slot

A named place holding one value plus a generation counter. Writing overwrites and bumps the counter; reading never blocks and returns the latest. Backed by memory or a wire — the reader can't tell.

Manifest

One file naming every slot and its wiring — who writes, who reads, its fresh_for window. Read once at boot, then frozen. Nothing is discovered at runtime, so the whole shape is checkable on a laptop.

Monitor

Wakes on a steady local beat and asks one thing per watched slot: did the generation move within its window? Yes → fresh, no → stale. Two answers, no clock. Everything else is composed from these.

Command topics have a single writer

Each actuator/command topic is produced by exactly one cog. On follower_segby that's balance producing :motor_target — one writer, so there is no arbiter and nothing to arbitrate. The arbiter is an optional seam that appears only when more than one source must command the same actuator: the controllers publish intents and an arbiter cog becomes the single producer, merging them by a tested priority.

Often you don't need it even with teleop in the mix — teleop can steer through the policy by adjusting the setpoint the policy consumes, leaving the policy as the single writer. The arbiter is only for the case where teleop bypasses the policy to command the actuator directly.

03Anatomy of a cog

A cog is a thin shell the framework provides, wrapped around the few things the user actually writes. The diagram shows the split: teal is yours (pure, hardware-free, unit-testable); gold is framework (everything with a clock or a socket).

So a sensor cog supplies a device binding + an edge transform; a controller cog supplies a step; an actuator cog supplies a safe-state mechanism. None of them supply transport, timing, supervision, or wire-identity. Section 6 and 7 show all three kinds in real code.

04One tick, end to end

This is the heart of "how it comes together." Follow a single 50 Hz control cycle from an IMU sample on the Blaster to torque at the wheels, crossing both wires. Notice that no participant knows the topology of any other — they exchange values on topics.

why this is debuggable Replay, not re-run

Because the law is pure — the shell, not the law, stamps the result — you can log the bus and the wire and replay the tick on a laptop: feed the recorded :pose stream into BalancePid.step and get deterministic outputs with no robot attached. Replay is bit-exact on the same target and tolerance-bounded across targets (floats round differently on ESP32 vs ARM vs x86), so it's ideal for logic bugs, not for chasing the last LSB. A control bug becomes "diff two value streams," not "re-create the fault on hardware."

05The wire: a value becomes a frame (and back)

Above the wire, everything is a value living in a named slot. On the wire, a value is a flat, fixed-layout frame wrapped in COBS framing with a CRC. The codec is the only place that knows the byte layout — data structure and serialization are separate things, so changing a payload never means hand-editing byte math in a cog.

0x00COBS delim
LEN1 B
TYPE1 B · slot id
ADDR1 B · cog.imu
FW_ID1 B · every frame
GEN2 B · generation
PAYLOADn B · value (+ t_dev if fusing)
CRC162 B
0x00COBS delim

The same value exists three times along its journey — a C struct on the Blaster, these bytes on the UART, an Elixir %Obs{} on the master — but it is conceptually one value in one slot. What crosses the wire to answer "is this still good?" is the generation: a small counter that bumps once per write. The reader compares it to the last it saw — moved means new, unmoved past its fresh_for window means stale — so the exact same fresh/stale check works for a slot in local memory and a slot three boards away, with no clock and nothing to synchronise. There is no edge timestamp in the frame: time is bought back only inside the payload of the few slots that fuse — a per-device monotonic stamp (§09) — never as a tax on every frame. The firmware id rides on every frame and is checked at the decode seam against a per-node expected value, so a mis-flashed board surfaces as a fault and is refused arming. Slot TYPEs live in a dedicated range; a small low range is reserved for platform/liveness frames so a value type can never collide with the liveness lane. Routing keys on ADDR, so one shared frame type carrying many sources is a table lookup, not a dispatcher special case.

ONE CONTRACT, GENERATED — THE WIRE CANNOT DRIFT

The frame layout, TYPE/ADDR constants, and codecs come from a single source of truth (topic_contract.ex); the C header is generated from it and a drift test fails the build if the on-disk header differs. The C constants physically cannot diverge from the Elixir definition, and byte-exact parity vectors stay as the cross-language witness for the codecs. This is what makes "a wire change is a codec bump plus a parity vector" safe rather than scary. A slot's freshness window and ring depth are manifest data, generated into the firmware the same way — see §09.

Lean by default

Counters on the wire carry only what disambiguates failure: crc_fail, resync, last_rx_age, bytes_in. Decorative histograms can wait — every new frame field is a version bump and a parity vector.

Three buckets, honestly

Those counters separate garbage-on-the-wire from nothing-on-the-wire from idle-but-alive. They cannot separate dead/unpowered/mis-wired — those all read bytes_in==0 and are a bring-up problem, not a runtime one.

Conflated, not queued

The link holds one pending slot per (type,addr). A fast producer overwrites its own slot; the wire carries the latest, never a backlog. Backpressure by construction, not by alarm.

06Master code — Elixir / OTP

The master is plain OTP, written in Elixir, running on the BEAM under Nerves on the Pi. Four pieces: the bus, the generic cog shell, a pure law, and the health authority — plus the supervision tree that composes them from the manifest.

ELIXIRplatform/cog_bus.exL3 · one bus, topics
defmodule CogBus do
  # ONE bus. Topics, not addresses. Transport-transparent: a subscriber gets a
  # value and never learns whether it came from this BEAM or three boards away.
  # CogBus is the interface; the backend is Phoenix.PubSub when a LiveView
  # dashboard shares the broker (:pg shown here for the minimal illustration).
  def subscribe(topic), do: :pg.join(:cog_bus, topic, self())

  def publish(topic, value) do
    for pid <- :pg.get_members(:cog_bus, topic), do: send(pid, {:cog_bus, topic, value})
    :ok
  end
end

ELIXIRplatform/cog_server.exthe shell that wraps a pure law
defmodule CogServer do
  use GenServer
  # Owns subscription, freshness, publishing and state-HOLDING.
  # The user writes only mod.init/1 and the pure mod.step/4.
  defstruct [:mod, :params, :produces, :fresh_for, :law, inputs: %{}, gen: %{}, idle: %{}]

  def start_link(spec), do: GenServer.start_link(__MODULE__, spec)

  @impl true
  def init(%{mod: mod, params: p, consumes: in_slots,
             produces: out, fresh_for: ff}) do
    Enum.each(in_slots, &Slot.subscribe/1)
    :timer.send_interval(beat_ms(ff), :step)     # the cog's OWN local beat — its only timing
    {:ok, %CogServer{mod: mod, params: p, produces: out,
                     fresh_for: ff, law: mod.init(p)}}
  end

  # On each beat: pull the latest of every input slot, see whose GENERATION moved,
  # and hand the law the freshness facts. No clock — staleness is idle beats.
  @impl true
  def handle_info(:step, st0) do
    st    = sample_inputs(st0)                    # {value, gen} per slot; reset idle if gen moved, else +1
    stale = for {slot, n} <- st.idle, n > st.fresh_for[slot], do: slot

    # The shell never invents a "safe value." It hands the law the freshness facts
    # and lets the law decide how to degrade.
    case st.mod.step(st.law, st.inputs, stale, st.params) do
      {:emit, setpoint, law} ->
        Slot.put(st.produces, %Cmd{type: st.produces, setpoint: setpoint})  # a write bumps the gen
        {:noreply, %{st | law: law}}
      {:no_command, law} ->                 # law can't act safely → write nothing;
        {:noreply, %{st | law: law}}         # the actuator's own dead-man takes over
    end
  end

  # pull each input slot; a moved generation resets its idle count, silence grows it
  defp sample_inputs(st) do
    Enum.reduce(Map.keys(st.fresh_for), st, fn slot, acc ->
      {v, g} = Slot.get(slot)
      moved? = g != Map.get(acc.gen, slot)
      %{acc | inputs: Map.put(acc.inputs, slot, v), gen: Map.put(acc.gen, slot, g),
              idle: Map.update(acc.idle, slot, 0, &(if moved?, do: 0, else: &1 + 1))}
    end)
  end
end
ELIXIRcogs/balance/balance_pid.exL5 · YOUR core logic — pure
defmodule BalancePid do
  # PURE. No process, no clock, no socket. Returns a plain value (the shell
  # stamps it). The integral is an explicit VALUE threaded through step/4.
  def init(_p), do: %{i: 0.0, prev: 0.0, last_set: 0.0}

  # step/4 is told which inputs are STALE and decides how to degrade —
  # the framework no longer guesses a "safe value" on our behalf.
  def step(law, _inputs, stale, _p) when :pose in stale,
    do: {:no_command, law}        # no angle ⇒ can't stabilise; the dead-man handles the fall

  def step(law, inputs, stale, p) do
    %Obs{payload: %{angle: a, rate: r}} = inputs[:pose]
    set = if :lean_setpoint in stale, do: law.last_set,  # range stale → hold last lean, stay upright
                                       else: setpoint(inputs[:lean_setpoint])
    err = set - a
    i1  = clamp(law.i + err * p.ki, p.i_max)
    u   = p.kp * err + i1 + p.kd * -r
    {:emit, clamp(u, 1.0), %{law | i: i1, prev: err, last_set: set}}
  end
end
ELIXIRplatform/health_monitor.exmonitors folded → one truth
defmodule HealthMonitor do
  use GenServer
  # PLATFORM, always-on. Health is just the FOLD of the slot monitors — no separate
  # service to keep in sync. Each watched slot is binary fresh/stale (did its
  # generation move within fresh_for ticks of this local beat — NO clock). A scope
  # folds to one word; criticality decides safe vs degraded. Scopes are manifest data.
  def start_link(scopes), do: GenServer.start_link(__MODULE__, scopes)

  @impl true
  def init(scopes) do
    watched = scopes |> Map.values() |> Enum.flat_map(& &1.watch) |> Enum.uniq()
    Enum.each([:link_stats, :loop_stats | watched], &Slot.subscribe/1)
    :timer.send_interval(20, :beat)            # the monitor's OWN local beat — the only timing it needs
    {:ok, %{scopes: scopes, gen: %{}, idle: %{}, levels: %{}, nominal_since: nil}}
  end

  @impl true
  def handle_info(:beat, s0) do
    s = sample_generations(s0)                  # per slot: did gen move? reset idle or +1
    levels = for {scope, spec} <- s.scopes, into: %{},
               do: {scope, derive(s, spec)}            # PURE per-scope fold of fresh/stale
    Enum.each(levels, fn {scope, lvl} ->
      Slot.put({:health, scope}, %Health{source: scope, level: lvl})
    end)
    global = worst(Map.values(levels))               # fold of scopes → one global truth
    Slot.put(:health, %Health{source: :global, level: global})
    s1 = track(s, global)
    maybe_validate_firmware(s1)                       # fires on first SUSTAINED global nominal
    {:noreply, %{s1 | levels: levels}}
  end

  # a scope folds its monitors: a CRITICAL slot stale floors to :safe; a non-critical
  # one stale is :degraded; everything fresh is :nominal. Binary in, three words out.
  defp derive(s, %{watch: w, critical: crit}) do
    cond do
      Enum.any?(crit, &stale?(s, &1))                  -> :safe
      Enum.any?(w -- crit, &stale?(s, &1))            -> :degraded
      loop_overrun?(s) or link_bad?(s)               -> :degraded
      true                                          -> :nominal
    end
  end

  # stale = the generation has not moved for longer than fresh_for ticks. No timestamps.
  defp stale?(s, slot), do: Map.get(s.idle, slot, 999) > fresh_for(slot)
end

CONTROL RUNS ON THE MASTER

Control — including a balance loop driven by reinforcement learning — runs on the master, where the policy and the learning live; an RL controller cannot be pushed onto a microcontroller. The master is therefore sized to meet its tightest loop's deadline. The BEAM is soft real-time, so the loop is given headroom (capable compute, kept clear of GC pressure and dashboard contention) and, crucially, it is measured: a LoopMonitor tracks per-tick interval and worst-case jitter and feeds :loop_stats into the one health truth, so a loop drifting toward its deadline shows up as degraded on the dashboard before it shows up as a fall. The actuator dead-man backstops the rare miss. Pushing a tight, fixed loop down to an edge MCU is an available option — not the default.

ELIXIRplatform/loop_monitor.exdeadline metrics → :loop_stats
defmodule LoopMonitor do
  use GenServer
  # Instruments a control loop: per-tick interval, worst case, rolling p99.
  # Publishes :loop_stats so HealthMonitor flags deadline pressure EARLY —
  # degraded long before a missed deadline becomes a fall.
  def tick(label), do: GenServer.cast(__MODULE__, {:tick, label, now_us()})

  @impl true
  def handle_cast({:tick, label, t}, s) do
    s = record(s, label, t - Map.get(s.last, label, t))   # update max + p99
    CogBus.publish(:loop_stats,
      %{label => %{p99_us: s.p99[label], max_us: s.max[label], budget_us: s.budget[label]}})
    {:noreply, %{s | last: Map.put(s.last, label, t)}}
  end
end

Same architecture, different runtime. The Blaster has no BEAM, no supervisor, no "let it crash" — so the framework's job on the microcontroller is a cooperative scheduler, bounded I/O, framing, and a watchdog. The cog author still only writes read + cook (sensors) or a dead-man (actuators).

ARDUINO-Cplatform/firmware/scheduler.cframework owns the loop, not the cog
/* Each on-Blaster cog = a cadence + a tick. Compute and schedule, decomplected.
   No cog runs its own timer; one loop drives them all.                        */
typedef struct { uint32_t period_us, last_us; void (*tick)(uint32_t now); } Task;

static Task tasks[] = {
  {   1000, 0, imu_sample_tick  },   /* sample IMU ~1 kHz                          */
  {  20000, 0, pose_report_tick },   /* cook + publish :pose at 50 Hz  (push-down) */
  {  50000, 0, range_report_tick},   /* :range at 20 Hz                            */
  { 100000, 0, heartbeat_tick   },   /* UNCONDITIONAL liveness                     */
};

void loop() {
  esp_task_wdt_reset();
  uint32_t now = micros();
  for (size_t i = 0; i < sizeof(tasks)/sizeof(*tasks); i++)
    if ((uint32_t)(now - tasks[i].last_us) >= tasks[i].period_us) {
      tasks[i].last_us = now;
      tasks[i].tick(now);
    }
  link_pump();   /* drain inbound frames, route by ADDR */
}

   transport, timing and identity belong to the framework.                    */

  float ax, az, gy;

}

}
ARDUINO-Cplatform/firmware/transport.cL2 · meaning-blind, conflated
/* Frames, CRC, conflation, counters. "Don't flood the wire" is enforced HERE,
   once, not in any cog.                                                       */
typedef struct { uint16_t crc_fail, resync, bytes_in; uint32_t last_rx_us; } LinkStats;
static LinkStats stats;

static Obs  pending[N_SLOTS];   /* one slot per (type,addr) */
static bool dirty[N_SLOTS];

void link_send(const Obs *o) {
  int s = slot_of(o->type, o->addr);
  pending[s] = *o; dirty[s] = true;          /* overwrite → intermediate dropped */
}

void link_pump(void) {
  if (hb_due()) write_frame(heartbeat_frame());  /* PRIORITY lane: liveness first, never conflated,
                                                   never subject to data backpressure → busy ≠ dead */
  for (int s = 0; s < N_SLOTS; s++)              /* data fills what's left of the budget */
    if (dirty[s]) { write_frame(cobs_crc_encode(&pending[s])); dirty[s] = false; }
  read_inbound(&stats);   /* decode; bad CRC bumps stats.crc_fail; fw_id mismatch → fault */
}

Two state machines run constantly: a per-device lifecycle (drives self-heal) and the health FSM, one instance per scope (drives that scope's floor and, via the global fold, firmware validation). They are deliberately separate machines — seeing a fault, recovering from it, and being safe in it are three concerns.

09The communication core — slot · manifest · monitor

Strip a robot down and almost every part is doing the same thing: reading a value someone else produced and deciding whether to trust it — a camera frame, a motor's reported angle, a "go" command. The hard part was never moving the bytes; it is knowing whether the bytes are still true. So the whole communication layer is the smallest thing that answers that one question, and everything else — safety, transport, health, recovery — is built out of it rather than bolted beside it.

one question, asked everywhere is this value still good?

Three primitives answer it. The slot holds data. The manifest says who's connected. The monitor decides fresh-or-stale. Learn these three and you've learned the system; the rest is composition. This section carries its own goals, principles and invariants — each a specialisation of §00 — because freshness is the core the whole framework stands on.

Sub-goals — what the communication core optimises for

Answer one question fast

Is this value still good? Everything is shaped to answer that — quickly, locally, and out of parts small enough to hold in your head.

No clock anywhere

A generation counter plus a local beat give freshness with no timestamps and nothing to synchronise across boards.

Fixed and checkable at boot

The whole shape is written down before anything moves, so a broken wire is caught on a laptop — not with a real arm swinging.

Memory known in advance

Overwrite-only by default; no unbounded queue. If one slot needs the last few, it opts into a fixed bounded ring — an exception it asks for, not a tax everyone pays.

Compose, don't extend

Power comes from composing the three primitives. Safety, transport, health and recovery are thin layers over them — nothing new to learn.

Few knobs to misset

Overwrite, a freshness window, a safe action. The big standards expose dozens of QoS settings; every knob is a way to misconfigure the robot.

Sub-principles — how the communication core thinks

  • T1 · Change-detection, not time. Freshness is "did the generation move?" — a counter, not a clock. The only timing anywhere is each monitor's own local beat; no two boards ever have to agree on a clock.
  • T2 · A slot holds the latest, never a backlog. Reads return the newest write and never block; overwrite-only is the default, so a fast producer can't drown a slow consumer and there is no queue to flood or to starve.
  • T3 · The shape is fixed at boot. The manifest names every slot and its wiring, read once and frozen — no runtime discovery, so the whole system is checkable before anything moves.
  • T4 · Two answers, not three. A monitor says fresh or stale; that is the only question a safety-relevant reader asks. The old "slow but alive" state cost a separate heartbeat channel and changed no decision — it's gone.
  • T5 · Power by composition, not extension. Safety, transport, health and recovery are thin layers over slot/manifest/monitor. You compose the core; you do not grow it.
  • T6 · Buy time back only in the payload. The core is clock-free. The one job that genuinely needs time — fusion that interpolates — carries a per-device monotonic stamp inside the payload of just its inputs, never as a field on every slot.

Sub-invariants — what must stay true

  • never  A value in a slot without a generation. A value re-presented as fresh though its generation never moved is the frozen-but-trusted field.
  • never  Freshness measured by a clock. It is generation-vs-local-beat, binary fresh/stale. No timestamps, no clock sync, no third "slow but alive" trust state.
  • never  A slot read but never written, or a reader that wants updates faster than its writer can produce. The boot check refuses it and prints the two slots and the two numbers that don't fit.
  • never  An unbounded queue or buffer. Overwrite-only, or an opt-in bounded ring that overwrites its oldest entry and never grows. A buffer you don't need is just a place for stale data to hide.
  • never  A timestamp in the core. Time lives only in the payload of the slots that fuse — bought back narrowly, never a system-wide tax.
  • always  The manifest is read once at boot and then frozen; nothing is discovered at runtime.
  • always  Exactly one writer per slot (written_by), enforced by the manifest — the single-writer rule, made structural.
  • always  The dead-man is a monitor wired to a plant-specific safe action, on its own chip, firing even if the master is gone.
  • check  A new slot earns its wiring: written_by, read_by, fresh_for, and rarely depth — all data, all checkable before power-up.

9.1 · The slot — a named box with a generation

A slot is a named place that holds exactly one value plus a counter called its generation. Writing overwrites the old value and adds one to the generation. Reads never wait and never queue — you get whatever is in the box right now. There are no timestamps; a slot records only how many times it has changed, not when.

ELIXIRthe slot — overwrite + a counter
# a write — overwrite the value, bump the counter
Slot.put("/imu/pose", pose)        # gen 41 -> 42

# a read — never blocks, always the latest
{value, gen} = Slot.get("/imu/pose")

To know "is this new?" you don't need to know when it arrived — only whether it changed. A reader remembers it last saw gen 41; next loop the slot says gen 44 — three writes happened, it just uses the latest. If it still says 41, nothing came. (Frames lost on a wire simply jump the generation; comparison is !=, not >, so it survives the counter wrapping.) A plain counter answers the freshness question on its own, with no clock and no clock-skew bugs.

9.2 · The manifest — who writes, who reads, fixed at boot

The manifest names every slot and says who is allowed to write it, who reads it, and how long it may sit unchanged. It is read once at startup and then frozen — nothing is discovered while the robot runs.

DATAa slot declaration — the wiring is just data
slot "/imu/pose",
  written_by: :imu,                 # exactly one writer — the single-writer rule, structural
  read_by:    [:balance, :health],
  fresh_for:  3                     # expect a new generation within 3 monitor ticks

Because the wiring is data, you can check it before the robot powers up: is anything writing /imu/pose? Is a cog reading a slot nobody fills? Does a reader want updates faster than the writer can produce? You trade the flexibility of plug-and-play for the certainty of knowing your whole system at boot — and for a single robot of known shape that is a good trade, which is exactly why DDS-style runtime discovery is left out: you already know which sensors are there, so say it once and check it once.

9.3 · The monitor — fresh or stale, nothing between

A monitor wakes on a steady local beat — say every 20 ms — and records each watched slot's generation. If the generation hasn't moved within its fresh_for window, the slot is stale; otherwise it's fresh. Two answers.

ELIXIRthe monitor — one comparison per slot, per beat
# on every local beat, per watched slot:
moved? = gen_now != gen_last        # a counter, compared — no clock
idle   = if moved?, do: 0, else: idle + 1
state  = if idle > fresh_for, do: :stale, else: :fresh

The only decision a safety-relevant reader makes is "trust this value — yes or no?" The arm watching the camera doesn't care why the camera went quiet; if its window passes with no new generation, it stops reaching and holds. The old design's third state ("slow but still alive") needed a whole separate heartbeat channel to detect and changed no decision, so it's cut — one less subsystem, same safety. The monitor's beat is local, so generation counters plus a local beat give freshness with no shared clock anywhere.

9.4 · Everything else is composed from the three

The features a real robot needs aren't new machinery — each is a thin layer over slot, manifest, and monitor.

  • Boot check — a plain function reads the manifest and refuses to start on wiring that can't work (a slot read but never written, a reader faster than its writer); it prints the two slots and the two numbers that don't fit. builds on → the manifest (it's data you can check).
  • Safety / the dead-man — "if /imu/pose goes stale, hold and cut motor power" is the whole safety system: a monitor result wired to one plant-specific action. It runs on its own small chip watching its own copy of the slot, so it fires even if the master crashes entirely. builds on → a monitor + one safe action.
  • Transport — a slot is a slot whether it's local memory or a wire to a microcontroller; the generation simply travels inside the frame (§05), so the same fresh/stale check works on-chip and across the robot. builds on → the slot (value + generation are all that crosses).
  • Health — fold every monitor's fresh/stale into one word: all fresh → nominal, a non-critical slot stale → degraded, a safety-critical slot stale → safe. No separate health service to keep in sync — health is the sum of answers the monitors already produce (§06). builds on → many monitors, aggregated by criticality.
  • Recovery — OTP supervisors restart crashed processes; firmware uses A/B images that roll back a bad update. Real and useful, but a different job from safety, kept deliberately apart — recovery restores software while the dead-man already held the physical world. builds on → supervision + A/B firmware, around the core, not inside it.

9.5 · The bounded ring — when you need the last few

Overwrite-only is the default and it is right almost everywhere. A handful of jobs need the last few values, not just the newest; for those a slot opts into a bounded ring. It isn't a new primitive — it's the same slot holding N values instead of one.

DATAa slot that keeps the last N — opt-in, off by default
slot "/imu/raw",
  written_by: :imu,
  read_by:    [:fusion],
  fresh_for:  2,
  depth:      8                     # keep the last 8 writes — default is 1

A new write overwrites the oldest entry; memory is fixed and known at boot (a depth-8 ring is eight boxes instead of one). The generation still increments on every write and a plain read still returns the newest value, so monitors and the manifest treat it exactly like an ordinary slot — only a reader that asks for the window ever sees history. One job genuinely needs it: fusion that interpolates, which has to find the two samples bracketing an instant. Reach for it there and almost nowhere else.

9.6 · Sensor fusion — two tiers, and where time comes back

Different sensors run at different speeds — an IMU at 1 kHz, a camera at 30 Hz. Mixed rates are free at the transport, because each is its own slot and there is no shared queue to flood. A fusion cog doesn't run on a wall clock — it runs when its inputs change, which is exactly what the generation already reports: cheap prediction on the fast input, expensive correction only when the slow input's generation moves.

Tier 1 · latest-wins

Read the newest of each input, check each is fresh via its monitor, combine. Right whenever the robot is slow relative to its sensors — a 30 ms-old frame doesn't matter if nothing moved that far in 30 ms. Costs nothing beyond the three primitives.

Tier 2 · time-aligned

For anything dynamic, "newest of each" is wrong — the two readings describe different instants. Put a capture stamp in the payload of just the fusion inputs (a per-device monotonic clock). This is the one place "no timestamps" is deliberately bought back.

Keeping it on the master keeps alignment to two cases: a sensor running locally stamps with the master's own monotonic clock; a sensor on a microcontroller is captured on its clock, so the master keeps a lightweight running offset between the two — carried on the heartbeat — and converts the capture time onto the master timeline. That offset exists only for fusion; the fresh/stale gating never touches it. And because consecutive same-device stamps are directly subtractable, the same payload field also lets you watch bus latency and jitter grow — production deltas against arrival deltas — with no clock sync, if and when you want that diagnostic.

degradation rides the same rails and the honest limit

If the camera goes stale its monitor already says so; the fusion cog keeps predicting on the IMU alone and marks its own output slot /state/pose degraded — or lets it go stale. Because that output is just another slot, the safety layer sees the trouble through the very same fresh/stale machinery; there's no special "fusion failed" signal to invent. The honest limit: the tightest fusion wants the IMU sample at the camera's capture instant, which means interpolating between the two that bracket it — that's the one job the bounded ring exists for. Sub-millisecond alignment across boards needs real clock sync (PTP) on top; pay that cost narrowly, on the fusion inputs only, and nowhere else.

all three together a camera, an arm, and a guard

A camera writes /camera/frame 30 times a second, each write bumping the generation. An arm reads the latest frame each control loop and aims the gripper — miss a frame and it just uses the newest, no backlog to drain. A guard on its own chip watches only the frame's generation; five ticks with no new generation cuts arm power, and it fires even if the main computer is dead. At boot the manifest confirms the camera writes the slot and both the arm and guard read it — or the robot refuses to start. Three primitives, one safe robot.

10How the library is laid out

The repository structure is the strata, and the dependency arrow points only downward: a bot is data + UI; cogs are reusable capabilities; platform is everything with a clock or a socket. Each home is one or more mix apps wired by path: deps, so the arrow is compiler-enforced: a cog cannot depend on a bot, and the platform cannot depend on a cog — it simply won't compile. Adding a bot touches only bots/; adding a capability touches only cogs/.

platform/                              # L0–L4 — every bot gets this free, never edits it
  master_runtime/  (mix app)          # the Elixir chassis; the bottom of the arrow

         health_monitor.ex loop_monitor.ex framing/ topic_contract.ex

the test of the whole design the size of your surface

To build a new bot from existing cogs, you write one manifest.exs and one dashboard.ex. To add a new capability, you write a device backend + a pure cook (sensor) or a pure step (controller) or a deadman (actuator) — and nothing in platform/. Because the boundary is compiler-enforced by the path:-dep graph, a cog or bot that tries to reach into platform/ won't compile — which is the signal a seam is missing, not that the framework needs a feature.

Where to go next

  • The remaining forks are hardware/bench calls: whether a CPU-independent hardware enable-drop is worth a board revision, and how deep the per-device self-heal FSM should go — the fail-passive floor stands without it, so self-heal can start shallow and deepen at the bench.
  • Natural first slice: stand up cog_bus + cog_server + one sensor cog + the health monitor on the master, with a fake Blaster feeding recorded frames — the whole upper stack is testable with no hardware because every interface is a value.
  • Then push down: port cook_pose from the master (where you prototyped it against logged samples) to the Blaster unchanged — the payoff of keeping it a pure, location-independent function.
