00Core principles, goals & invariants

Read this first. It is the contract the rest of the document implements — the why behind every seam. When you extend the framework, come back here: a change that violates an invariant below is almost always letting two concerns that can vary independently share one home.

Goals — what we optimise for

Stated as outcomes, not features. Every design decision traces to one of these.

Compose, don't build

A new robot is assembled from existing cogs through a manifest. You write core logic; the framework owns the plumbing.

Declare, don't wire by hand

From the consumer's side it is a composable system of cogs: you declare which cogs you want and how they connect. The framework owns all the non-declarative work — moving commands and readings, checking the link follows through, deciding if a signal is fresh, surfacing an error.

Fail into legibility

A fault names itself — what broke, and where — and never collapses into ambiguous silence.

Safe in the gap

The robot reaches a safe state on any fault, independently of the part that failed, never depending on recovery succeeding.

Reason locally

You can understand and change one cog without holding the whole system in your head.

Test without hardware

Core logic is pure and replayable: develop on a laptop, reproduce a run from a log of values.

Right-rate, not max-rate

Move only the information that is needed, when it is needed. Never flood a wire or a CPU.

Evolve without rewrites

Add a cog, move it to another node, or swap a control law by editing data, not by rippling code.

Principles — how we think

The tenets that produce those goals. Mostly one idea: concerns that can vary independently live in separate homes.

  • 01 · Keep concerns separate. What a cog computes, when it runs, how it crosses the wire, what happens when it breaks, and which node it lives on are five separate things — never one object.
  • 02 · Prefer values and pure functions. Push as much of the system as possible into immutable data and input→output functions; reserve processes for what genuinely owns time or a socket.
  • 03 · Values carry a counter, not a clock. Every slot value carries seq, a counter the producer bumps by one on each write. Freshness is change-detection — did seq advance within a window of the consumer's own local beat — so it needs no shared clock anywhere. A producer's local t_dev rides along too, used only for same-device differences (jitter, fusion time-alignment, replay), never to compare one node's clock to another's.
  • 04 · One space of named slots; name slots, not nodes. Producers and consumers name slots, never each other. A value flows through a named place that holds the latest write. Whether a slot is backed by local memory or copied across a wire is hidden from both sides — a reader cannot tell local from remote.
  • 05 · Transport is meaning-blind. A link moves bytes and counts failures; it never knows what a value means. Consumers read a value, never a frame.
  • 06 · Detect, be safe, recover — three jobs. Seeing a fault, being safe in it, and recovering from it are different jobs with three separate homes.
  • 07 · Supervision recovers code; an independent floor keeps the actuator safe. A restart is never the safe-state mechanism. The floor lives on the actuator's own chip and drives the plant to its safe action on silence — so it fires even if the master is entirely gone. The safe action is plant-specific (zero torque for the balancer).
  • 08 · Configuration is data; mechanism and safety are code. Numbers (gains, thresholds, windows) live in the manifest; the safety transition graph is tested code, never authored by a bot.
  • 09 · Declare, pick, validate — one rail. A cog declares a contract — what it consumes and produces, the rate range its hardware allows, which gains are tunable and within what bounds, its safe action and arm gate. The wiring picks concrete values within that contract. The framework validates every pick against the cog's declared limits and refuses to start on any pick that does not fit. No negotiation, no solver — one bounds check, run on a laptop before power-up. Rate, type-match, freshness window and tunable range are all the same check. A cog ships its own contract, so the same cog drops into different bots and each bot picks differently within its limits.
  • 10 · Build in dependency order. Nothing above is sound until the layer beneath it is true: bounded I/O before monitors before health rows.

Invariants — what must stay true when you change things

The guardrails. Before merging a change, check it against every line. The italic clause is the tell — the symptom that you are about to break the invariant.

  • never  A cog owns transport, scheduling, supervision, or wire-identity. If a change has a cog reaching for a socket or a timer, a seam is missing — add the seam, don't thicken the cog.
  • never  A value crosses a slot without a seq. A frozen-but-trusted field — a value re-presented as fresh though its seq never moved — is exactly the failure the counter exists to catch.
  • never  The manifest decides whether to enter the safe state. It may set thresholds; the transition graph stays in tested code.
  • never  A second data plane or an optional "health cog." A fault is a counter-plus-reason in an ordinary slot; liveness is the platform's reserved low slot range. Health is the fold of monitors that already exist, scoped per subsystem (:health/limb_a…) and folded to one global word — not a separate service to keep in sync.
  • never  More than one producer per command slot. One writer per command slot. When several sources must command one actuator, an arbiter cog becomes that single writer and merges their intents by a tested priority.
  • never  Freshness measured by a clock, or a raw time gate in the manifest. A slot is fresh when its seq moved within the consumer's fresh_for window, counted in the consumer's own beats — never a wall-clock age. fresh_for is a multiple of the writer's period, so a window shorter than one write cannot be expressed.
  • always  Every device read is bounded; every link send is bounded by construction. This is a precondition — establish it before anything above assumes "non-blocking."
  • always  A new reader is born stale, and a new stateful component engages the floor while recovering. A fresh or rebooted reader distrusts whatever value is sitting there until it personally witnesses a new write. A restart is not a safe state.
  • always  The pure core stays pure. Tempted to put I/O or a clock inside a step or a cook? Thread state as a value and lift the effect into the shell.
  • always  The actuator floor survives total master loss — and it is tested. The dead-man lives on a different chip; if the master is gone entirely, torque still zeros on silence.
  • always  The master is sized to meet its tightest control loop, and that margin is monitored. Soft real-time is fine with headroom plus a fail-passive floor; surface worst-case loop latency before it bites — don't discover it in a fall.
  • check  Adding a bot or a cog must not require editing platform/. If it does, that is the signal to add a seam, not a feature.
  • check  A new wire field earns its place. Every frame change is a codec bump through the generator, and the drift test must pass — not free bytes.
  • check  Never display confidence you cannot observe — and no counter without an incrementer. A green chip, or a counter hardcoded to 0, with no real signal behind it is worse than none; each counter needs a test proving it actually moves.

Capabilities — what the design delivers

The features that fall out of the principles above. Each is a property of the framework, free to every bot.

compose

Cogs composed into bots from a single manifest — composition-as-data, read once at boot, then frozen.

contract

Every cog ships a contract — slots in/out, a rate range, tunable bounds, safe action. The wiring picks values; construction validates each pick and fails loudly on an out-of-range or mis-typed connection, on a laptop.

pure

Replayable core logic: develop and unit-test on a laptop; reproduce any run by re-feeding a recorded value log into step.

edge

Push-down processing with backpressure by conflation — cook fast at the edge, report at the producer's declared rate.

wire

Transport-transparent comms over UART / CAN / serial — the same code whether a value is local or three nodes away.

health

Health truth per subsystem (scopes) folded to a global nominal / degraded / safe, driving the dashboard, the log, and firmware validation.

fail-passive

An independent floor at every actuator — a comms-independent dead-man on the actuator's own chip — driving the plant to its safe action when the command goes silent.

heal

Per-device self-heal: bounded re-probe behind the device seam — online for soft sensors, at-rest only for load-bearing actuators, never live-energising one mid-task.

recover

OTP supervision on the master; A/B firmware that is made permanent only after a node's own slots show sustained healthy function, reverted otherwise.

observe

Honest link counters (CRC-fail / resync / last-rx-age) that separate garbage from silence from idle-but-alive.

deadline

Control-loop deadline monitoring — per-tick interval and worst-case jitter are tracked and folded into health, so timing pressure appears on the dashboard before it appears as a fall.

re-home

Location independence — move a cog to a different node by editing data, then regenerate and reflash; no code rewrite.

arbitrate

Single-writer command slots. When several sources must command one actuator, an optional arbiter cog is the sole producer, merging intents by a tested priority — otherwise it isn't there.

freshness

Clock-free freshness — seq plus a local beat answer "is this still good?" as binary fresh-or-stale, with no timestamp and no clock sync. The whole communication core is three primitives (§09).

mixed

Mixed runtime — a BEAM/Elixir master with C/Arduino cogs (or Elixir on the ESP32 via AtomVM).

ecosystem

Integrates into BeamBots — define the bot in its topology DSL, surface each off-BEAM cog as a BB.Sensor/BB.Actuator view, and reach the microcontroller it can't (§11).

One sentence to hold all of it: keep the cog thin, make every value carry a counter and a local timestamp so freshness needs no shared clock, answer "is it flowing?" with the counter and "is it real?" with the cook, and keep detecting a fault, being safe in it, and recovering from it as three separate jobs — and never let a restart, a single fresh frame, or a stale intent pretend to be a safe state or an arming.

01The system at a glance

Three nodes, two wires, one space of named slots on the master. Signal is cooked at the edge and reported upward as low-rate values; intent flows downward and is gated by a fail-safe floor on the actuator's own chip. Colour tells you which stratum each box belongs to. Underneath all of it sit just three ideas — slot · manifest · monitor, detailed in §09; the rest of this document is what you build out of them.

Master / platform (Elixir) sensors node (Arduino-C) wheels node (Arduino-C) values in slots
Slot

A named place holding one value plus two stamps: seq, a counter the producer bumps by one on every write, and t_dev, the producer's own local time at that write. Writing overwrites; reading never blocks and returns the latest. Backed by memory or a wire — the reader can't tell.

Manifest

One file naming every node, every slot, and its wiring — who writes, who reads, its fresh_for window. Read once at boot, then frozen. Nothing is discovered at runtime, so the whole shape is checkable on a laptop before power-up.

Monitor

Wakes on a steady local beat and asks one thing per watched slot: did seq advance within its fresh_for window? Yes → fresh, no → stale. Two answers, no shared clock. Everything else is composed from these.

A command slot has a single writer

Each command slot is produced by exactly one cog. On follower_segby that is balance producing :motor_target — one writer, so there is no arbiter and nothing to arbitrate. An arbiter is a seam that appears only when more than one source must command the same actuator: the controllers write intent slots and an arbiter cog becomes the single writer of :motor_target, merging them by a tested priority.

Teleop can steer through the policy by adjusting the setpoint slot the policy reads, which leaves the policy as the single writer. The arbiter is for the case where teleop bypasses the policy to command the actuator directly.

03Anatomy of a cog

A cog is the software unit the user writes, plus a thin shell the framework wraps around it. The diagram shows the split: teal is yours (pure, hardware-free, unit-testable); gold is framework (everything with a clock or a socket). A node is the physical board a cog runs on; the two are never confused.

Each kind of cog supplies a small pure core and nothing else. A sensor cog supplies a device binding plus a cook that turns a window of raw samples into {:ok, value} or :invalid. A controller cog supplies a step that is told which inputs are stale and decides how to degrade. An actuator cog supplies a plant-specific safe action for its floor. None of them supply transport, timing, supervision, or wire identity — the shell owns all of that. Sections 6 and 7 show all three kinds in real code.

The cog interface — a pure core plus a contract

The pure core is one half of what a cog author writes; the other half is the contract — a small block of data that declares everything the framework needs to wire the cog safely without ever reading its code. The contract is the cog's public face, and it is deliberately short. These are the only eight things an author states; everything else (slot ids, freshness windows in beats, wire budget, firmware schedules) the framework derives from them.

Declare · pick · validate

The contract is half of one rail that runs through the whole framework (principle 09). The cog declares its limits; the bot's wiring picks a concrete value inside them; construction validates the pick and refuses to start if it does not fit. There is no negotiation and no solver — the framework never searches for an optimum. You say 50 Hz; if that is inside the cog's range it stands, and if it isn't, the build fails on a laptop and prints the cog, the limit, and the value that broke it. One bounds check, run before any hardware moves.

What makes this powerful is that every wiring decision is the same check. Rate, type-match, the freshness window, and a tunable gain are all "is this pick inside that declared range?" — so there is one rule to learn, not four. And because a cog declares limits rather than fixing a number, the same published cog drops into many bots: a temperature cog that can sample [0.1, 10] Hz is read every 5 s in one bot and every 30 s in another, each a legal pick; ask for 5 kHz and construction refuses it. The constraint lives where the truth lives — on the cog, next to the hardware that imposes it.

a slot is constrained from both ends because a cog is bidirectional

A cog is not always a producer — an actuator consumes a command. So a rate limit is not "the producer's rate"; it is a constraint on the slot, contributed by whichever side touches it. A sensor constrains its slot from the output side ("I can produce pose up to 1 kHz"); an actuator constrains its command slot from the input side ("drive me no slower than 10 Hz or my floor fires"). The picked rate must satisfy every constraint on the slot, so a 5 Hz controller wired to that actuator is a construction error — the dead-man-versus-rate mismatch is caught on a laptop, not discovered in a fall. The wire-budget check (§09) is the same idea at the link level: it confirms all the rate picks on a link have room to coexist.

One value, resolved as late as is safe and no later. A rate is fixed at construction and frozen into the generated firmware. A safety window or an arm gate is compiled in, because the floor must hold even if the master is gone — it can never wait on a runtime value. Only a tunable gain resolves at runtime, and only inside its compiled-in bounds. The author picks values; the value's safety role picks when it binds.

04One tick, end to end

Follow a single 50 Hz cycle of follower_segby from an IMU sample to torque at the wheels, crossing both wires. No participant knows where any other lives. Each one reads or writes a slot by id and never names a peer.

The freshness seam at the cog

The balance cog samples :pose on its own beat and asks its monitor one question: did :pose's seq advance within the fresh_for window? If :pose is stale, the law is told so and degrades — a balancer with no fresh angle returns "no command". The shell then writes nothing, so :motor_target's seq stops moving. The cog never invents a safe value; it simply stops producing.

The freshness seam at the actuator

The motor cog on wheels runs a monitor of its own, on its own chip: it watches :motor_target's seq against its local beat. When the seq stops advancing within the window, the floor drives zero torque — the safe action for a balancer. The floor lives on the actuator's own chip, so it fires even if the master is entirely gone.

balance/step.exElixir
# Pure: state in, value + next state out. No clock, no socket.
# `fresh` carries the slot values whose seq advanced in-window;
# `stale` names the slots whose seq did not.
def step(st, fresh, stale, params) do
  if :pose in stale do
    # No fresh angle → no trustworthy command this beat.
    # Returning :no_command means the shell does not write,
    # so :motor_target seq freezes and the floor on wheels engages.
    {:no_command, st}
  else
    {err, i} = integrate(st.i, params.setpoint - fresh.pose.tilt)
    u = params.kp * err + params.ki * i + params.kd * fresh.pose.rate
    {clamp(u, params.u_limit), %{st | i: i}}
  end
end
why this is debuggable Replay, not re-run

The law is pure and the shell — not the law — stamps the result, so the recorder logs each beat's record: the fresh inputs and their seqs, the stale set, the parameters, the law's incoming state, and the emitted output. Replaying is literally re-feeding that record into BalanceLaw.step and getting the same output, with no robot attached. Replay is exact on the same target and tolerance-bounded across targets, because floats round differently on an MCU than on the master. A control bug becomes "diff two value streams," not "re-create the fault on hardware."

05The wire: a value becomes a frame (and back)

Above the wire, everything is a value living in a named slot. On the wire, that value is a flat, fixed-layout frame wrapped in framing with a CRC. The codec is the only place that knows the byte layout — the data and its serialization are separate concerns, so changing a payload never means hand-editing byte math inside a cog.

The same value exists three times along its journey — a C struct on the wheel board, these bytes on the UART, an Elixir term on the master — but it is conceptually one value in one slot. There is exactly one identity on the wire: the slot id. The frame never names a producer. What crosses to answer "is this still flowing?" is the seq: a counter the producer bumps by one on every write. The reader compares it to the last seq it saw — moved means a new write, unmoved past its fresh_for window means stale — so the exact same fresh/stale check works for a slot in local memory and a slot three boards away, with no clock and nothing to synchronise. The frame also carries t_dev, the producing node's own 64-bit monotonic time at the write. It is never compared across nodes; the freshness check never reads it. It is carried so a fusing reader can time-align same-device samples, so per-producer latency and jitter are observable, and so a recorded run replays against its own in-band clock; it is 64-bit so a node's monotonic clock never wraps in the field. The firmware id rides on every frame and is checked at the decode seam against the value expected for that slot's node, so a mis-flashed board surfaces as a fault and is refused arming — it is two bytes because folding only one byte would let a wrong image alias to a clean one. Slot ids live in a dedicated range; a small low range is reserved for platform frames — liveness, arming, global stop — so a value slot id can never collide with the platform lane. Routing keys on the slot id through the generated topology: a hub forwards a number toward the side that produces or consumes that slot, a table lookup, never a peer-name dispatch.

ONE CONTRACT, GENERATED — THE WIRE CANNOT DRIFT

The frame layout, the slot ids, the codecs, and the per-slot routing all come from the manifest through one generator. The C headers are generated from it, and a drift test fails the build if a generated header on disk differs from the manifest. The C constants physically cannot diverge from the Elixir definitions, and byte-exact parity vectors stand as the cross-language witness for the codecs. A slot's fresh_for window is manifest data, generated into the firmware the same way — see §09. Because fresh_for is a multiple of the writer's nominal period, a window shorter than one write cannot even be expressed.

Lean by default

Link counters carry only what disambiguates failure: crc_fail, resync, last_rx_age, bytes_in. Decorative histograms stay off the wire — every new frame field is a codec bump and a parity vector.

Three buckets, honestly

Those counters separate garbage on the wire from nothing on the wire from idle but alive. They cannot separate dead from unpowered from mis-wired — those all read bytes_in == 0 and are a bring-up problem, not a runtime one.

Conflated, not queued

The link holds one pending value per slot. A fast producer overwrites its own pending value; the wire carries the latest, never a backlog. Bandwidth is slots × window rate × frame size, independent of bursts.

wire/decode.exElixir
def decode(frame) do
  with {:ok, %{slot_id: id, fw_id: fw, seq: seq, t_dev: t, payload: raw}} <- unframe(frame),
       {:ok, entry} <- Topology.lookup(id) do          # one slot-id table lookup
    if fw == entry.expected_fw do
      value = entry.codec.decode(raw)                    # the codec owns the byte layout
      Slot.put(id, value, seq, t)                        # atomic write of the whole row
    else
      Fault.bump(:fw_mismatch, slot: id)                 # mis-flashed board → refused arming
    end
  else
    :error -> Link.bump(:unknown_slot)                   # unknown id: dropped and counted, never guessed
  end
end

06Master code — Elixir / OTP

The master is plain OTP, written in Elixir, running on the BEAM under Nerves on the Pi. Five pieces: the slot table, the generic cog shell, a pure law, the health fold, and the loop instrument — composed into a supervision tree from the manifest.

ELIXIRplatform/slot.exone named in-memory table
defmodule Slot do
  # The slot space is ONE named in-memory table. A slot is one row:
  # {value, seq, t_dev}. get is one lookup; put is one atomic write of the
  # whole row, so a reader can never see a torn value/stamp. Reads never
  # block and return the latest. The table is owned by a tiny holder with
  # a standby heir at node lifetime, so the truth survives any restart.
  def get(id), do: :ets.lookup_element(:slots, id, 2)   # {value, seq, t_dev}

  def put(id, value) do
    seq = :ets.update_counter(:seq, id, 1)            # producer bumps seq by one per write
    :ets.insert(:slots, {id, {value, seq, mono_us()}}) # t_dev = this node's own monotonic clock
    :ok
  end
end

  # The author writes only mod.init/1 and the pure mod.step/4.

  @impl true
  def init(%{mod: mod, params: p, produces: out, fresh_for: ff}) do
    :timer.send_interval(beat_ms(ff), :step)     # the cog's OWN local beat — its only timing
    {:ok, %CogServer{mod: mod, params: p, produces: out,
                     fresh_for: ff, law: mod.init(p)}}  # idle starts empty → every input born STALE
  end

  # On each beat: PULL the latest of every input slot, see whose SEQ advanced,
  # and hand the law the freshness facts. No clock — staleness is idle beats.
  @impl true
  def handle_info(:step, st0) do
    st    = sample_inputs(st0)                    # {value, seq} per slot; reset idle if seq moved, else +1
    stale = for {slot, n} <- st.idle, n > st.fresh_for[slot], do: slot

    # The shell never invents a "safe value." It hands the law the freshness facts
    # and lets the law decide how to degrade. params come from a slot too (live tuning).
    case st.mod.step(st.law, st.inputs, stale, st.params) do
      {:emit, setpoint, law} ->
        Slot.put(st.produces, %Cmd{type: st.produces, setpoint: setpoint})  # a write bumps seq, stamps t_dev
        {:noreply, %{st | law: law}}
      {:no_command, law} ->                 # law can't act safely → write NOTHING;
        {:noreply, %{st | law: law}}         # seq freezes → the actuator's own floor takes over
    end
  end

  # pull each input slot; an advanced seq resets its idle count, silence grows it
  defp sample_inputs(st) do
    Enum.reduce(Map.keys(st.fresh_for), st, fn slot, acc ->
      {v, seq, _t_dev} = Slot.get(slot)
      moved? = seq != Map.get(acc.seq, slot)
      %{acc | inputs: Map.put(acc.inputs, slot, v), seq: Map.put(acc.seq, slot, seq),
              idle: Map.update(acc.idle, slot, 999, &(if moved?, do: 0, else: &1 + 1))}
    end)

defmodule HealthMonitor do
  use GenServer
  # Health is the FOLD of the slot monitors that already exist — no separate
  # service to keep in sync. Each watched slot is binary fresh/stale (did its
  # SEQ advance within fresh_for beats of this local beat — NO clock, NO t_dev).

  @impl true
  def init(scopes) do
    :timer.send_interval(20, :beat)            # the monitor's OWN local beat — the only timing it needs
    {:ok, %{scopes: scopes, seq: %{}, idle: %{}, levels: %{}, nominal_since: nil}}
  end

  @impl true
  def handle_info(:beat, s0) do
    s = sample_seqs(s0)                          # per slot: did seq advance? reset idle or +1
    levels = for {scope, spec} <- s.scopes, into: %{},
               do: {scope, derive(s, spec)}            # PURE per-scope fold of fresh/stale
    Enum.each(levels, fn {scope, lvl} ->
      Slot.put({:health, scope}, %Health{source: scope, level: lvl})
    end)
    global = worst(Map.values(levels))               # fold of scopes → one global truth
    Slot.put(:health, %Health{source: :global, level: global})
    s1 = track(s, global)
    maybe_validate_firmware(s1)                       # fires on first SUSTAINED global nominal
    {:noreply, %{s1 | levels: levels}}
  end

  # a scope folds its monitors: a CRITICAL slot stale floors to :safe; a non-critical
  # one stale is :degraded; everything fresh is :nominal. The actuator's own status
  # slot is watched too, so a floored or rebooted board can never read green.
  defp derive(s, %{watch: w, critical: crit}) do
    cond do
      Enum.any?(crit, &stale?(s, &1))                  -> :safe
      Enum.any?(w -- crit, &stale?(s, &1))            -> :degraded
      loop_overrun?(s) or link_bad?(s)               -> :degraded
      true                                          -> :nominal
    end
  end

  # stale = the seq has not advanced for longer than fresh_for beats. No timestamps.
  defp stale?(s, slot), do: Map.get(s.idle, slot, 999) > fresh_for(slot)
end

CONTROL RUNS ON THE MASTER

Control — including a balance loop driven by reinforcement learning — runs on the master, where the policy and the learning live; an RL controller does not fit on a microcontroller. The master is therefore sized to meet its tightest loop's deadline. The BEAM is soft real-time, so the loop is given headroom (capable compute, kept clear of GC pressure and dashboard contention) and, crucially, it is measured: a LoopMonitor tracks per-tick interval and worst-case jitter and feeds :loop_stats into the one health truth, so a loop drifting toward its deadline shows up as degraded on the dashboard before it shows up as a fall. The actuator floor (§8) backstops the rare miss. A tight, fixed loop can also be placed on an edge MCU — that is a data edit in the manifest, then regenerate and reflash.

09The communication core — slot · manifest · monitor

Strip a robot down and almost every part is doing the same thing: reading a value someone else produced and deciding whether to trust it — a camera frame, a motor's reported angle, a "go" command. The hard part is not moving the bytes; it is knowing whether the bytes are still true. So the whole communication layer is the smallest thing that answers that one question, and everything else — safety, transport, health, recovery — is composed from it.

one question, asked everywhere is this value still good?

Three primitives answer it. The slot holds data. The manifest says who is connected. The monitor decides fresh-or-stale. Learn these three and you have learned the system; the rest is composition. This section carries its own goals, principles and invariants — each a specialisation of §00 — because freshness is the core the whole framework stands on.

Sub-goals — what the communication core optimises for

Answer one question fast

Is this value still good? Everything is shaped to answer that — quickly, locally, and out of parts small enough to hold in your head.

No shared clock

A write counter plus each reader's own local beat give freshness with no clock comparison between boards, so there is nothing to synchronise.

Fixed and checkable at boot

The whole shape is written down before anything moves, so a broken wire is caught on a laptop — not with a real arm swinging.

Memory known in advance

Overwrite-only by default; no unbounded queue. A slot that needs the last few values opts into a fixed bounded ring — an exception it asks for, not a tax everyone pays.

Compose, don't extend

Power comes from composing the three primitives. Safety, transport, health and recovery are thin layers over them — nothing new to learn.

Few knobs to misset

Overwrite, a freshness window, a safe action. Each knob is a way to misconfigure the robot, so there are very few.

Sub-principles — how the communication core thinks

  • T1 · Change-detection, not time. Freshness is "did seq advance?" — a counter, not a clock. The only timing anywhere is each monitor's own local beat; no two boards ever have to agree on a clock.
  • T2 · A slot holds the latest, never a backlog. Reads return the newest write and never block; overwrite-only is the default, so a fast producer cannot drown a slow consumer and there is no queue to flood or to starve.
  • T3 · The shape is fixed at boot. The manifest names every slot and its wiring, read once and frozen — no runtime discovery, so the whole system is checkable before anything moves.
  • T4 · Two answers, not three. A monitor says fresh or stale; that is the only question a safety-relevant reader asks. "Still flowing?" is answered by seq; "still real?" is answered separately by the cook. Two questions, kept apart.
  • T5 · Power by composition, not extension. Safety, transport, health and recovery are thin layers over slot/manifest/monitor. You compose the core; you do not grow it.
  • T6 · Time only as same-device differences. The core decides freshness with no clock. Every value still carries the producer's own monotonic t_dev, used only as differences on the same device — for fusion that time-aligns samples, for latency and jitter statistics, and as the in-band clock that makes a run replayable. No two clocks are ever compared.

Sub-invariants — what must stay true

  • never  A value in a slot without a seq. A value re-presented as fresh though its seq never advanced is a frozen-but-trusted field.
  • never  Freshness measured by comparing two clocks. It is seq-advance witnessed within the reader's own local beat, binary fresh/stale. No clock sync, no third "slow but alive" trust state.
  • never  A slot read but never written, or a reader whose fresh_for window is shorter than its writer's period. The boot check refuses it and prints the two slots and the two numbers that do not fit.
  • never  An unbounded queue or buffer. Overwrite-only, or an opt-in bounded ring that overwrites its oldest entry and never grows. A buffer you do not need is just a place for stale data to hide.
  • never  t_dev read by the freshness check. Freshness uses only seq and the reader's local beat; t_dev is for same-device differences and for replay, never for trust.
  • always  The manifest is read once at boot and then frozen; nothing is discovered at runtime.
  • always  Exactly one writer per slot (written_by), enforced by the manifest — the single-writer rule, made structural.
  • always  The floor is a monitor wired to a plant-specific safe action, on the actuator's own chip, firing even if the master is gone.
  • always  A reader starts stale: it distrusts whatever value is sitting there until it personally witnesses a new write, so every restart is safe by construction.
  • check  A new slot earns its wiring: written_by, read_by, fresh_for, and rarely depth — all data, all checkable before power-up.

9.1 · The slot — a named box with a counter and a stamp

A slot is a named place that holds exactly one value plus two stamps: a counter called seq and the producing node's own monotonic time t_dev at the write. Writing overwrites the old value and adds one to seq. Reads never wait and never queue — you get whatever is in the box right now. The whole row (value, seq, t_dev) is written atomically, so a reader can never see a torn value-and-stamp.

ELIXIRthe slot — overwrite the row, bump the counter
# a write — overwrite value + stamps as one row; bump seq
Slot.put("/imu/pose", pose, t_dev)   # seq 41 -> 42

# a read — never blocks, always the latest
{value, seq, t_dev} = Slot.get("/imu/pose")

To know "is this new?" you do not need to know when it arrived against your own clock — only whether seq moved. A reader remembers it last saw seq 41; next loop the slot says seq 44 — three writes happened, it just uses the latest. If it still says 41, nothing came. (Frames lost on a wire simply jump seq; the test is "did it advance", which survives the counter wrapping.) A plain counter answers the freshness question on its own, with no clock comparison and no skew bugs. The t_dev stamp rides along untouched by that decision — it is the producer's own clock, used later only as same-device differences.

9.2 · The manifest — who writes, who reads, fixed at boot

The manifest names every slot and says who is allowed to write it, who reads it, and how long it may sit unchanged. It is read once at startup and then frozen — nothing is discovered while the robot runs.

DATAa slot declaration — the wiring is just data
slot "/imu/pose",
  written_by: :imu,                 # exactly one writer — the single-writer rule, structural
  read_by:    [:balance, :health],
  fresh_for:  3                     # tolerate 3 missed writes — a multiple of the writer's period

Because the wiring is data, you can check it before the robot powers up: is anything writing /imu/pose? Is a cog reading a slot nobody fills? Is a reader's window shorter than one of the writer's periods? This boot check is the validate step of the one rail from §03 — declare on the cog, pick in the manifest, validate at construction — here applied to the slot graph: a pick that names a missing producer, double-writes a slot, mis-matches a type, or sets an impossible window is refused on a laptop, with the two slots and the two numbers that do not fit. You trade the flexibility of plug-and-play for the certainty of knowing your whole system at boot — and for a single robot of known shape that is the right trade, because you already know which sensors are there, so you say it once and check it once. The window is expressed as a multiple of the writer's nominal period, so "a window shorter than one write" cannot even be written down.

9.3 · The monitor — fresh or stale, nothing between

A monitor wakes on a steady local beat — for follower_segby, every 20 ms at 50 Hz — and keeps, per watched slot, three things: whether it has ever seen the slot (seen), the last seq it saw, and the local beat at which that seq last moved. If seq has not advanced within its fresh_for window, the slot is stale; otherwise it is fresh. Two answers.

ELIXIRthe monitor — one comparison per slot, per beat
# on every local beat, per watched slot:
{_value, seq_now, _t_dev} = Slot.get(slot)
moved? = seen and seq_now != seq_last   # a counter, compared — no clock
idle   = if moved?, do: 0, else: idle + 1
state  = if seen and idle <= fresh_for, do: :fresh, else: :stale

A freshly started reader has not yet witnessed a write, so seen is false and it is born stale: it distrusts whatever value happens to be sitting in the slot until it personally sees seq advance. This is what makes a restart safe — a rebooted board never trusts a leftover reading. The only decision a safety-relevant reader makes is "trust this value — yes or no?" The balancer watching the obstacle distance does not care why the reading went quiet; if its window passes with no new seq, it stops reaching for it. "Is the producer still flowing?" is this seq question; "is the value real?" is a separate question answered by the cook (§04). The monitor's beat is its own, so a counter plus a local beat give freshness with no shared clock anywhere.

9.4 · Everything else is composed from the three

The features a real robot needs are not new machinery — each is a thin layer over slot, manifest, and monitor.

  • Boot check — a plain function reads the manifest and refuses to start on wiring that cannot work (a slot read but never written, a reader window shorter than its writer's period); it prints the two slots and the two numbers that do not fit. It also adds up each link's traffic — Σ(slot rate × frame size) against the link's baud — and refuses a topology that over-subscribes the busiest wire; because every slot streams every beat, that budget is load-bearing now, not advisory. builds on → the manifest (it is data you can check).
  • Safety / the floor — "if the command slot goes stale, drive to the plant-specific safe action" is the whole dead-man: a monitor result wired to one safe action. It runs on the actuator's own chip watching its own copy of the command slot, so it fires even if the master is entirely gone. builds on → a monitor + one safe action.
  • Transport — a slot is a slot whether it is local memory or a wire to a microcontroller; the value, seq and t_dev travel verbatim inside the frame (§05), so the same fresh/stale check works on-chip and across the robot, and a reader cannot tell local from remote. builds on → the slot (value + stamps are all that crosses).
  • Health — fold every monitor's fresh/stale into one word: all fresh → nominal, a non-critical slot stale → degraded, a safety-critical slot stale → safe. No separate health service to keep in sync — health is the fold of answers the monitors already produce (§06). builds on → many monitors, folded by criticality.
  • Recovery — OTP supervisors restart crashed processes; firmware uses A/B images that roll back a bad update. Real and useful, but a different job from safety, kept deliberately apart — recovery restores software while the floor already held the physical world. builds on → supervision + A/B firmware, around the core, not inside it.

9.5 · The bounded ring — when you need the last few

Overwrite-only is the default and it is right almost everywhere. A handful of jobs need the last few values, not just the newest; for those a slot opts into a bounded ring. It is not a new primitive — it is the same slot holding N values instead of one.

DATAa slot that keeps the last N — opt-in, off by default
slot "/imu/raw",
  written_by: :imu,
  read_by:    [:fusion],
  fresh_for:  2,
  depth:      8                     # keep the last 8 writes — default is 1

A new write overwrites the oldest entry; memory is fixed and known at boot (a depth-8 ring is eight boxes instead of one). seq still advances on every write and a plain read still returns the newest value, so monitors and the manifest treat it exactly like an ordinary slot — only a reader that asks for the window ever sees history. One job genuinely needs it: fusion that interpolates, which has to find the two samples bracketing an instant. Reach for it there and almost nowhere else.

9.6 · Sensor fusion — two tiers, and where time is used

Different sensors run at different speeds — an IMU at 1 kHz, a ranging sensor at 30 Hz. Mixed rates are free at the transport, because each is its own slot and there is no shared queue to flood. A fusion cog does not run on a wall clock — it runs when its inputs change, which is exactly what seq already reports: cheap prediction on the fast input, expensive correction only when the slow input's seq advances.

Tier 1 · latest-wins

Read the newest of each input, check each is fresh via its monitor, combine. Right whenever the robot is slow relative to its sensors — a 30 ms-old reading does not matter if nothing moved that far in 30 ms. Costs nothing beyond the three primitives.

Tier 2 · time-aligned

For anything dynamic, "newest of each" describes different instants. The t_dev each value already carries is the per-device capture stamp; fusion time-aligns the samples by their same-device t_dev differences. This is the one place the framework uses time at all.

Fusion lives on the master, so alignment has two cases. A sensor running locally stamps t_dev with the master's own monotonic clock. A sensor on a microcontroller stamps t_dev with its own clock, so the master keeps a lightweight running offset between the two and converts the capture time onto the master timeline. That offset exists only for fusion; the fresh/stale gating never touches it. And because consecutive same-device t_dev stamps are directly subtractable, the same field lets you watch bus latency and jitter — production deltas against arrival deltas — with no clock sync, whenever you want that diagnostic.

degradation rides the same rails and the honest limit

If the ranging sensor goes stale its monitor already says so; the fusion cog keeps predicting on the IMU alone and marks its own output slot /state/pose degraded — or lets it go stale by not writing. Because that output is just another slot, the safety layer sees the trouble through the very same fresh/stale machinery; there is no special "fusion failed" signal to invent. The honest limit: a single sensor cannot catch its own subtle-but-plausible failure — a reading that is wrong yet varies plausibly. That needs a second source, which is precisely the job fusion exists for; it is out of scope for one sensor's cook. Sub-millisecond alignment across boards needs real clock sync on top; pay that cost narrowly, on the fusion inputs only, and nowhere else.

all three together the obstacle, the wheels, and the floor

A ranging sensor writes /range/front 30 times a second, each write advancing seq. The balancer reads the latest distance each 50 Hz loop and trims the wheels to hold its set gap — miss a reading and it just uses the newest, no backlog to drain. The floor on the wheel board watches only the command slot's seq; a window of beats with no new seq drops to zero torque, and it fires even if the master is dead. At boot the manifest confirms the sensor writes the slot and the balancer and health read it — or the robot refuses to start. Three primitives, one safe robot.

10How the library is laid out

The repository structure is the strata, and the dependency arrow points only downward.

A bot is composition data plus UI. A cog is a reusable capability — a pure cook, a pure step, or a floor, plus the contract that travels with it (§03). Because a cog carries its own contract, it is publishable and droppable into any bot: the bot picks values inside the contract, never restating it. The platform is everything that holds a clock or a socket. Each home is one or more mix apps wired by path: deps, so the arrow is compiler-enforced: a cog cannot depend on a bot, and the platform cannot depend on a cog. The build refuses the reverse edge. Per-node firmware — schedule, routing, configuration — is generated from the manifest, never hand-written.

A natural order to stand it up

  • First slice, no hardware: bring up the slot table, a cog shell, one sensor cog, and the health fold on the master, with a fake node link feeding recorded frames. The whole upper stack is testable without a board, because every interface is a slot.
  • Then push down: port cook_pose from the master — where it was prototyped against logged samples — to the MCU unchanged. That is the payoff of keeping it a pure, location-independent function: it runs the same on either runtime.
  • Self-heal deepens at the bench: the per-device validation and revert FSM can start shallow and grow, because the fail-passive floor stands without it. 11Relationship to the BeamBots ecosystem

BeamBots (the bb framework) is the natural home for everything above the wire: a Spark DSL for the robot's topology, a supervision tree that mirrors its structure, a hierarchical PubSub, and free dashboards (bb_liveview, bb_kino) and kinematics (Nx-backed IK). It has one boundary we sit exactly outside of: every BeamBots node runs Elixir on the BEAM — its drivers are GenServers, its hardware hangs off the one machine running the BEAM. Our reason to exist is the case BeamBots does not cover: cogs that do not run Elixir, on microcontrollers reached over a bus we define ourselves. So we do not replace BeamBots; we extend it downward, joined at one seam — proven by prototype to fit, with a thin conformance layer we own (§11.4).

THE ONE LINE — ELIXIR ABOVE IT, OUR PROTOCOL BELOW

Define the bot in BeamBots. Surface each off-BEAM cog to it as an ordinary BB.Sensor or BB.Actuator. Below that seam runs our wire — COBS+CRC over UART / I²C / CAN, carrying seq, t_dev, fw_id, the freshness core, and the on-chip floor. BeamBots sees components; it never sees the microcontroller. The framework above the line is consumed; the package below it (bb_cog) is what a BeamBots user adds to reach hardware that isn't running Elixir.

11.1 · The seam is BB.Sensor and BB.Actuator

A BeamBots driver is not a GenServer you write — you supply callbacks and the framework wraps them (BB.Sensor.Server / BB.Actuator.Server). That division is ours already: the author supplies a pure core, the framework owns the process. The mapping onto our cog is direct.

11.2 · Safety crosses the line carefully — the floor stays ours

BeamBots' BB.Actuator requires a disarm/1 that "makes the hardware safe." Read naïvely, that would make a BEAM callback — reachable only over the wire — the thing that stops a motor, contradicting our load-bearing invariant that the floor survives total master loss. The prototype settled exactly how to read it, and the answer is reassuring: BB.Safety is humble. Its own moduledoc says the BEAM is soft-real-time only and that you must implement hardware-level safety as the primary protection; report_error/3 is pure notification and does not disarm; it never reads back whether the hardware actually went safe. So the trap we feared — BeamBots quietly asserting ownership of safety — is not real.

disarm/1 = a fast path, never the guarantee

It sends a disarm frame down the wire when the master is alive — quick and observable. It may fail to reach the node, and the authoritative safe-state is still the on-chip dead-man firing on seq-staleness. BeamBots safety is one cause feeding our "many causes, one actuation" disarm (§Point 5).

Safety truth flows up the wire — for observers

The node's status slot (floor_engaged, armed, applied_seq) republished onto PubSub is the real truth, and it drives dashboards and our own logic. Proven limit: it does not drive BB.Safety's armed bit — there is no status→safety path in BeamBots at all.

the real trap — the inverse of the one we feared a feedback-free green light

Because BB.Safety's armed? is flipped only by arm/disarm/force_disarm and never by inbound status, its belief and the node's ground truth diverge silently: after a link-drop or an on-chip floor event, BeamBots can still read armed while the wheels are floored. Anything that treats BB.Safety.armed? as "is the hardware live?" — an operator, a UI, an interlock — will be wrong in exactly the moments that matter. The §00 principle holds across the line, now sharper: never display confidence you cannot observe — so a "physically live?" signal must be read from the status slot, never from armed?.

And disarm/1 is "lie or lock," so we must choose its meaning deliberately. The prototype pinned BeamBots' behaviour: disarm/1 returning :ok drives the robot to :disarmed (so a best-effort path that returns :ok on a dropped frame makes BeamBots confidently wrong); returning {:error, …} or raising drives it to :error and locks out re-arming until force_disarm/1. Neither value means "the floor will handle it." So we make disarm/1's return mean exactly what BeamBots thinks — "the disarm intent was delivered/acknowledged" — and drive every "is it physically safe?" decision from the status slot instead. One proven gotcha tightens this: auto-registration with BB.Safety is a doc lie — you must call BB.Safety.register/2 in init, or disarm/1 is never invoked, and only a warning tells you.

Cogs report; the master coordinates

The first instinct — wire a status→BB.Safety adapter so BeamBots' armed? tracks reality — is the wrong primitive, and grilling the design replaced it with a cleaner separation. A cog has no business deciding for its siblings; it cannot see them. So a cog only ever reports its own state truthfully — "I am cog X, I floored", or even a softer "I am running hot" that no reflex would catch — and that report always flows to the master (when the link is open) through the surviving LinkOwner. The master owns coordination: a distinct coordination policy (master-side tested code, not a manifest knob and not a cog) reads the health fold plus the raw reports and decides what a given cog's state means for the rest of the robot — propagate a stop to a scope, broadcast a global one (the §Point 6 e-stop slot), or merely log a degradation. It may initiate a stop, not only relay one, because the trigger (a warning, a dangerous combination of degraded states) may exist where no single cog has floored.

THE SAFETY STACK — THREE LAYERS, EACH A FALLBACK FOR THE ONE ABOVE
  1. Coordination policy (master, in the BB tree) — preemptive & coordinated stops from whole-system judgment. Richest, least reliable, best-effort. May initiate. An ordinary crash just restarts it born-stale, and it re-derives from the current fold — restart is the recheck, no resume logic. The one state it does not auto-recover from is a topology teardown — and there BeamBots has already force-disarmed everything, so there is no decision left to make.
  2. BeamBots force-disarm / broadcast e-stop (master-driven) — the blunt global stop when the topology collapses or an operator commands it. Commands stop advancing.
  3. The floor (on each chip) — reflexive, autonomous, survives total master loss. The guarantee. Never depends on layers 1–2.

Because the policy is strictly additive on top of the floor, none of this is recovery-dependent safety (which §00 forbids). The standing principle that makes it all simple: safe is the default state; motion is what must be continuously earned. No layer has to act to reach safety — each only ever stops authorising motion, and every chip floors on command-silence on its own. You never make the robot safe; you only keep earning motion — a fresh, witnessed, in-window, chip-gated command.

The policy's shape: one robot-wide pure decide/3 plus a thin shell. It is a sibling of HealthMonitor on its own beat — sample, decide, actuate — where all the judgment is a pure, tested function and the shell only reads slots and emits the chosen action. It is robot-wide, not per-scope, because coordination is inherently cross-scope (a per-scope policy could never see a cross-limb coupling); it consumes the per-scope fold and adds only the cross-scope layer.

Input — facts and warnings, kept apart

The per-scope fold levels (already-derived hard facts) plus the raw soft-warning fields the fold deliberately does not gate on (a temp_c on :motor_status, say). A floor/stale/wedge is already :safe in the fold; the policy never re-litigates it — it only initiates and escalates.

Output — three actions, existing actuators

:none → log · {:stop_scope, s} → bump that scope's :estop counter (§Point 5, read directly by the cog) · :stop_global → write the broadcast e-stop slot (the §Point 6 broadcast frame; its 0x0000 slot-id allocation is §Point 7). It writes no command slot and never re-arms — re-arm is always the chip-gated nonce sequence.

The rule is two ideas: a soft warning alone is a log; a warning plus corroborating degradation, or a declared dangerous coupling, is a stop — and a tripped coupling that spans more than one scope escalates to global. That keeps it from being trigger-happy: one warm sensor on an otherwise-nominal scope only logs; hot-and-degraded, or hot on two coupled limbs, stops. The code/manifest split holds the §00 line: decide/3 — the escalation graph, "warning alone ≠ stop" — is tested code; the manifest adds only couplings: (named sets of scopes dangerous-together) and the warning thresholds. The manifest cannot express "stop on one warm sensor" — that conjunction lives in the graph, not in a knob. A boot check enforces that a status field is either fold-critical or policy-soft, never both, so one fact has one home. On follower_segby — one scope, no couplings, no soft-warning field — decide/3 degenerates to "fold says :safe → already handled; else :none": a near-empty pass-through, correct because a one-actuator bot has no sibling to coordinate. Complexity appears only when a bot declares a coupling.

11.3 · One node, several cogs, one bus — owned beside the tree

A single ESP32 may host an IMU cook and a motor floor at once, so several BeamBots components share one physical link. The prototype opened that link inside a component's init/1 and proved the lifecycle holds against BeamBots' real supervisor — a crashed component restarts :one_for_one, init re-runs, the bus re-opens cleanly (ownership is a Registry key released on owner death; no double-open, no leak), and the reborn reader is born-stale (§Point 2). But grilling that result surfaced a sharper question the prototype's shape ducked: which of the N components' init owns the shared bus, and what happens to the bus when that one is force-disarmed? So the design pulls bus ownership out of the components entirely.

The bus is owned by a dedicated LinkOwner process that lives beside BeamBots' topology subtree, not inside it (the canonical OTP shape: a process owns the resource, everyone else talks through it). The components become thin views that read and write slots through the LinkOwner; they own no socket. The payoff is the §00 goal fail into legibility: when BeamBots tears the topology down (§11.4 below), the components die but the LinkOwner survives in the infrastructure zone — so the status stream keeps flowing and a robot that has gone to :error does not also go blind. Per-cog vs. one composite-component-per-node is an ergonomics call we lean toward per-node and finalise as we build.

The boundary between a component and the LinkOwner is a slot, not a call API — they share only named ETS slots, never a reference or a message. This is the only shape that honours transport-transparency (a reader cannot tell local from remote); the instant you give a component a LinkOwner.read/2 call you have rebuilt the CogBus that §Point 2 deleted — a second data plane with a mailbox that can be told apart from a local read. So the views are almost stateless: a BB.Sensor is a beat loop that Slot.gets its inbound slot, runs its born-stale witness, and lifts a fresh value into a typed BB.Message to BB.publish; a BB.Actuator is a one-line handler that decodes a command and Slot.puts the outbound command slot. All wire work — framing, conflation, status decode, the safety de-escalation — lives in the LinkOwner, which polls the same slots on its own beat.

SlotSingle writerReader / drain

The load-bearing row is the middle one: the LinkOwner is a read-only drain of the command slot, never its writer. This is forced, not stylistic — a LinkOwner serving N cogs over one bus must never be the writer of a per-cog command slot (that makes it an N-writer), and more sharply, a LinkOwner that could write the command could bump seq and manufacture a false advance — exactly what would break the "surviving LinkOwner is safe by construction" guarantee below. As a drain it can only re-send the same seq, which no floor trusts. The single-writer rule and the survival guarantee pin each other. (The slot→BB.Message-type mapping a sensor view needs is generated manifest data, drift-tested like the codecs — never hand glue that can silently diverge from the contract.)

why the surviving LinkOwner is safe no flush needed

A LinkOwner that outlives a force-disarm keeps a stale command or a stale arm-intent sitting in BEAM memory — and keeps draining it to the wire. That is harmless by construction, not by cleanup: re-sending a stale value is the same seq re-arriving, never an advance, so the chip's born-stale floor witness is never moved by it, and the reborn arm cog mints a strictly higher arm_seq than any survivor (§Point 2 read-back). We deliberately do not flush stale slots on tear-down — a flush would make safety depend on the flush succeeding at the worst moment, which is the recovery-dependent safety §00 forbids. Distrusting the un-witnessed is cheaper and stronger than scrubbing the stale.

the lifecycle gap the prototype found — and how LinkOwner closes it whole-topology teardown is terminal

Born-stale and clean bus re-open are correct-by-construction for an ordinary :one_for_one restart. But one level up, when BeamBots' topology supervisor stops (its restart budget exhausted), BB.Safety monitors it and force-disarms the whole robot into :error, leaving infrastructure alive — a terminal, whole-robot reaction with no component init to re-open the bus. Had the bus lived in a component's init, it would simply vanish here. Owning it in the beside-the-tree LinkOwner is exactly what resolves this: the bus is not a child of the dying subtree, so it survives the force-disarm, keeps status flowing, and is released or re-armed deliberately — never left half-open by a tear-down it didn't participate in. The terminal state is rare (it means components were crash-looping past budget); recovery is operator-driven, and until then every chip sits floored by default. The robot is safe because nothing is commanding it, not because anything had to act.

11.4 · VALIDATED — THREE PROTOTYPES AGAINST REAL bb 0.20.3

The three open questions were closed by three throwaway prototypes built against the real bb package (Elixir 1.18 / OTP 27), each green and committed. Every core bet held; the corrections above are what the spikes taught us.

  • Seam — ✅ fits. A cog contract maps onto options_schema/0; decode→BB.publish and BeamBots-command→encode both work. Caveats folded into §11.1: validation is boot-time not compile-time, the actuator command path needs self-subscribe, readings lift into typed BB.Message.
  • Safety — ✅ compatible, model corrected. The "BeamBots owns safety" trap is not real; the inverse (feedback-free armed?) and the "lie-or-lock" disarm/1 are. Folded into §11.2.
  • Supervision — ✅ both sub-gaps hold against BeamBots' real supervisor: born-stale survives a restart, the bus re-opens cleanly. The topology-force-disarm lifecycle gap is folded into §11.3.

The one conclusion all three reached independently: our value at this seam is a thin generation / conformance layer. From a cog contract, generate the BB.Sensor / BB.Actuator views (whose options_schema is the contract, whose init self-subscribes the command path and registers with BB.Safety, whose decode/encode lifts wire frames to/from BB.Message types) and the beside-the-tree LinkOwner that owns the bus and survives a force-disarm. The seam fits; the glue we own is what closes BeamBots' gaps — compile-time contract guarantees, command-path subscription, status-driven truth (cogs report, the master coordinates), and a bus lifecycle that survives both restart and force-disarm.
